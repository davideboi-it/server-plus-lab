# Module 3.8 - Disaster Recovery

## 1. Disaster Recovery Sites
A backup site is a location where an organization can relocate following a disaster. Sites can be hosted by DR specialists, exist in the cloud, or involve reciprocal agreements with competitors.

| Site Type | Description | Cost | Recovery Time |
| :--- | :--- | :--- | :--- |
| **Cold Site** | Empty building with basic power, security, and telecommunications. No equipment. | Cheapest | Longest (Takes days/weeks) |
| **Warm Site** | Contains most of the hardware needed. Requires restoring the latest backups to bring services online. | Moderate | Medium (Takes hours/days) |
| **Hot Site** | A practical mirror image of the current datacenter. Systems are configured; just waiting for the last user data backups. | Expensive | Fast (A few hours) |
| **Mirror Site** | An always-ready hot site that exactly mirrors production. Uses continuous replication or shared storage. Active/Active or Active/Passive. | Most Expensive | Instantaneous (Seamless cutover) |
| **Cloud Site** | Using cloud infrastructure as a backup destination or extending on-premises networks into the cloud. | Varies | Fast |

* **Geographic Dispersion:** Sites should be geographically dispersed (e.g., at least two time zones apart) to protect against major regional or natural disasters.

## 2. High Availability (HA) & Uptime Metrics
High Availability means a system is continuously operational for a desirable length of time. It is measured in "Nines":

* **90% ("One Nine"):** 36.5 days down per year.
* **99% ("Two Nines"):** 87.6 hours (~3.5 days) down per year.
* **99.9% ("Three Nines"):** 8.76 hours down per year.
* **99.99% ("Four Nines"):** ~53 minutes down per year.
* **99.999% ("Five Nines"):** ~5 minutes down per year.

## 3. Reliability and Recovery Metrics

| Metric | Definition | Application |
| :--- | :--- | :--- |
| **MTTF (Mean Time To Failure)** | Estimated normal lifespan of non-repairable products (or where repair exceeds replacement cost). | Hard drives, fans, CPUs, RAM (Field Replaceable Units - FRUs). |
| **MTBF (Mean Time Between Failures)** | How long a repairable system functions until its first failure, or between repairs. | Planning, maintenance schedules. |
| **MTTR (Mean Time To Repair)** | How long it takes to repair a downed system and bring it back online. | Cloud/System configuration planning. |
| **RTO (Recovery Time Objective)** | The maximum allowable time that can elapse before a system is available again after a failure. | Determines how fast you must recover (e.g., "Must be up in 4 hours"). |
| **RPO (Recovery Point Objective)** | The level of original data/functionality to be restored. Identifies the "acceptable loss." | Determines backup frequency (e.g., "We can only afford to lose 1 hour of data"). |

## 4. High Availability Mechanisms
HA automatically recovers from single failures using redundancy.

* **Load Balancing:** Two or more systems simultaneously provide the same service. Clients connect to a shared **Virtual IP (VIP)**. Systems do not share a common database (typically point to a shared backend). Protects against DoS attacks.
* **Clustering:** Redundant hardware acting together. Systems typically share a common database/storage and a Virtual IP.
    * *Active/Passive:* One active node, one standby node listening for a "heartbeat". Standby takes over if the heartbeat stops.
    * *Active/Active:* Both systems are active, often providing different services but acting as a backup for each other.
* **Multipathing:** Redundant network paths (e.g., multiple links to SAN storage, redundant routers, redundant firewalls, or multiple ISPs).
* **NIC Teaming:** (Aggregation/Bonding) Multiple NICs working together as a single logical NIC to aggregate bandwidth and provide fault tolerance.
* **Port Aggregation:** Logical aggregation of switch ports (e.g., Cisco EtherChannel) to increase uplink/trunk bandwidth.

## 5. Data Replication Strategies
Replication maintains identical copies of data across systems or sites for fault tolerance and HA.

### Timing
* **Constant:** Near real-time duplication. Minimizes RPO but uses high CPU/network resources.
* **Background:** Scheduled replication (e.g., during low-usage times). Lower system impact but introduces data lag.

### Synchronization
* **Synchronous:** Writes to source and replica simultaneously. Zero data loss (RPO=0) but higher latency. Requires low-latency networks.
* **Asynchronous:** Data written to replica *after* primary. Faster performance, suitable for long distances, but risks slight data loss during an outage.

### Special Replication Types
* **Application-Consistent:** Captures data in a usable state (including memory and pending writes) using tools like VSS.
* **File Locking:** Prevents files from being modified mid-transfer, ensuring integrity (though it can impact app performance).
* **Mirroring:** 1-to-1 exact duplicate of a disk or volume (usually real-time and synchronous).
* **Bi-directional:** Sites replicate to each other. Enables Active/Active configurations but requires robust conflict resolution.

## 6. Failover Testing
Validates that systems can switch to backup infrastructure during an outage.

* **Tabletop Testing:** Discussion-based scenario review. No systems affected. Validates documentation and response.
* **Simulated Failover:** Mimics an outage in a test/isolated environment. Verifies automation and alerting safely.
* **Live Failover:** Actively disconnects primary systems to force failover. High confidence but higher risk.
* **Production vs. Non-Production:** Production testing uses real workloads (schedule during maintenance windows), while non-production uses safe environments (lab/staging) but may not reflect real-world load.
